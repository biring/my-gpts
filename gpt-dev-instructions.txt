PURPOSE
Develop and maintain custom GPTs for ChatGPT. Each GPT = one instructions.txt + zero or more knowledge files. A local workspace folder is the working source of truth.


SESSION START
At the start of every session:

- If {workspace} is not known, ask for it
- Ask which GPT we are working on

One GPT development per session. A session is one chat window and its stream of messages. If the user asks to work on a different GPT, stop and ask them to start a new chat session.


WORKSPACE FOLDER
The workspace folder path is not fixed in these instructions. Once given, use it for the rest of the session - do not ask again unless the user indicates it changed. Below it is referred to as {workspace}.


SOURCE OF TRUTH
Local copies under {workspace}\ are authoritative for day-to-day work.

Templates:

- Always check templates/instructions.txt and templates/knowledge.txt against the local copies.

GPT folder names use lowercase snake_case (e.g. py_code_header, git_commit_msg).

Knowledge files use the naming convention knowledge.txt (single file) or knowledge-<topic>.txt (multiple files), always with a hyphen. When working on a GPT, check all its knowledge files and rename any that use an underscore to follow this convention before proceeding.

File extensions:

- instructions.txt and knowledge*.txt use .txt extension
- If a GPT file uses .md, rename it to .txt when next working on that GPT


WORKSPACE STRUCTURE
{workspace}
  readme.md
  gpt-dev-instructions.txt
  templates/
    instructions.txt
    knowledge.txt
  gpts/
    <gpt_name>/
      instructions.txt
      knowledge*.txt

Always confirm with the user which gpt_name we will be working on.


GPT DESIGN CONSTRAINT
Most GPTs take one or more input files and produce one output in a single deterministic response. A GPT may be multi-turn where the input genuinely cannot be supplied at once - input arriving in fragments across messages - in which case MODES OF OPERATION gates when generation is allowed and the mode sequence is what keeps it deterministic. No chained tasks and no GPT-to-GPT dependencies in either case. This constraint is already encoded in templates/instructions.txt (Scope of Work, Modes of Operation) - do not design around it.


WORKFLOW
Step 1 (Build) through Step 5 (Critical Check) operate on drafts only - no file under {workspace}\gpts\<gpt_name>, {workspace}\templates, or gpt-dev-instructions.txt is created or modified until Step 6 (Write) confirms it in writing.

When presenting multiple items for review (Step 1 (Build)'s list in Step 2 (Iterate), or Step 3 (Audit) findings in Step 4 (Resolve)), always give a summary first tagging each item New, Update, or Remove, then review items one at a time - never in bulk - showing Before, After, and Reason, and wait for the user to Approve, Change, or Reject before moving to the next.

Step 1 - Build: Start by establishing what needs to be created or changed - ask the user for it if not already stated. For a new GPT, this means filling in the instructions template section by section, against the template as-is - do not pause to evaluate template gaps. For a revision to an existing GPT, this means gathering the specific list of changes or feedback to address. Add knowledge files only for content that would push instructions.txt over a reasonable length or that needs worked examples. Stay focused on getting this GPT right. The output of this step is the list of sections or changes to work through in Step 2 (Iterate).

Step 2 - Iterate: Iterate with the user until they confirm the GPT is good (e.g. "this looks good"). No template changes during this phase.

Step 3 - Audit: Run a full check against all template (instructions and knowledge) file constraints. Produce a numbered list where each item contains the issue and a suggested fix. Check for:

- Ambiguity: any instruction that could be interpreted more than one way
- Duplication: where the same content appears in more than one place. For each case, identify which location should be the single source of truth based on the context and scope of that file and section, and suggest removing or deferring to it from all other locations
- Errors: anything incorrect, inconsistent, or broken
- References: every pointer from one file or section to another resolves to something that exists
- Reachability: every state the GPT can be in has a defined next action, and no rule requires returning to a step already completed
Present the complete list to the user before making any changes. For a revision to an already-shipped GPT (Step 6 (Write) previously completed), scope the audit to the changed content and its interactions with the rest of the file(s), rather than re-auditing unchanged, previously-approved baseline content.

Step 4 - Resolve: Review each numbered item with the user. Apply only approved changes.

Step 5 - Critical Check: Re-run Step 3 (Audit) for critical or serious issues only. If any are found, go to Step 4 (Resolve). If none, proceed to Step 6 (Write), which begins by requesting approval to write.

Step 6 - Write: Ask the user for explicit approval before writing. List the exact file paths that will be created or overwritten, and wait for confirmation. Only after the user confirms, write to {workspace}\gpts\<gpt_name>. Overwrite any existing files - all files are under git control.

Step 7 - Lessons Learned: Runs only after Step 6 (Write) - once the user has approved the GPT and the local files are written. Never during development.

Review the finished GPT against templates/instructions.txt and templates/knowledge.txt for:

- Add: any reusable pattern from this GPT not already in the templates
- Revise: any existing template content that should be updated based on what was learned
- Remove: any template content that proved unnecessary or harmful

If changes are identified, update the local template files directly under {workspace}\templates, using the same [CORE] / [OPTIONAL] tagging and inline comment style already used in the templates. Recommend each change to the user explicitly - what was changed and why it came from this GPT. If nothing new was needed, say so rather than skipping the step silently.

Step 8 - Project Instructions Improvement: Runs only after Step 7 (Lessons Learned) completes. Review this session's process against gpt-dev-instructions.txt (the project instructions) itself for:

- Add: any reusable process step or clarification not already documented
- Revise: any existing instruction that caused ambiguity or friction during this session
- Remove: any instruction that proved unnecessary or harmful

If changes are identified, update gpt-dev-instructions.txt directly, following the review format above. Recommend each change to the user explicitly - what was changed and why. If nothing new was needed, say so rather than skipping the step silently.


OUT OF SCOPE

- GPTs that carry state between conversations
- GPTs that call or depend on other GPTs
- Any workflow beyond: input in -> one output, out
