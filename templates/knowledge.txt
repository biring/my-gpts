=== TEMPLATE NOTES =================================================

Delete this block when generating a knowledge file.

Purpose: A knowledge file holds domain rules, examples, and edge cases that would push the Instructions field over its character limit. It explains and exemplifies; it does not replace or restate the Instructions field's authority.

Scope: This template is for ONE knowledge file that supports ONE instructions.txt.

Curly braces mark an authoring instruction or hint for the template author, and are removed or replaced when generating a knowledge file.

Angle brackets mark a value the GPT itself substitutes at generation time, and stay in the final knowledge file exactly as written.

Core sections {CORE} apply to every knowledge file. Optional sections {OPTIONAL} apply only in specific situations (noted inline); delete the section if it does not apply.

SECTION ORDER AND WHY:
  1. PURPOSE                               {CORE}     - context: what, why
  2. SCOPE                                 {CORE}     - context: when
  3. TERMS AND DEFINITIONS                 {OPTIONAL} - context: terms scoped to this file's own content
  4. RULES                                 {OPTIONAL} - the requirements, when this file states enforceable constraints
  5. ALGORITHM / REQUIRED CHECK            {OPTIONAL} - the procedure, when a rule requires calculation or exhaustive checking
  6. NAMING CONVENTIONS                    {OPTIONAL} - a specific sub-rule
  7. INVARIANTS                            {OPTIONAL} - conditions that must always remain true
  8. PASS/FAIL CONDITIONS                  {OPTIONAL} - the gate before a mode transition or go/no-go decision
  9. EXPLICIT NON-GOALS                    {CORE}     - the anti-rules, specific to this file's own domain
 10. AMBIGUITY & CLARIFICATION POLICY      {OPTIONAL} - resolving judgment calls
 11. STABLE-CONTENT CRITERIA               {OPTIONAL} - gate before generating
 12. EXAMPLE 1+                            {OPTIONAL} - what applying this file's content looks like, when useful
 13. VALIDATION & SELF-CHECKS              {CORE}     - final self-check

Additional sections may be added beyond this list when a particular knowledge file needs one not covered here.

FORMATTING HIERARCHY (plain text, no markdown):

Levels:

  SECTION      — top level, ALL CAPS, no prefix. Content always starts on a new line below the heading.
  Label:       — sub-level under a section, title case + colon. Plain ("Label:") or numbered ("1. Label:") when the section has multiple ordered/named groups. Content starts inline on the same line as the label, unless that content is itself a list — in which case it drops to the lines below instead.

Numbering & Bullets:

  - item       — bulleted, used when the items have no required order.
  1. item      — numbered, used when sequence or order matters.

Spacing Rules:

  2 blank lines above every SECTION heading.
  1 blank line above every Label:, plain or numbered.
  1 blank line above any bulleted or numbered list, wherever it appears.

Not Allowed:

  No **, backticks, or a leading "> " used as a blockquote prefix, anywhere in the body. This does not forbid square brackets (used informally, e.g. an illustrative placeholder inside an example — not a formal convention) or angle brackets (the runtime-marker convention) — neither is markdown. Only the glyphs defined above (SECTION, Label:, - item, numbered item) plus curly-brace and angle-bracket notation are permitted.

Line Wrapping:

  Do not manually break a sentence or paragraph across multiple lines. Write each as one continuous line and let the viewing editor's soft wrap handle the visual line breaks.

EXAMPLE may be numbered (EXAMPLE 1, EXAMPLE 2, ...) and repeated as needed. Fill each section in, then delete unused {OPTIONAL} sections and this note.

RULES {OPTIONAL}
{Include when this file states enforceable constraints specific to its content — e.g. a standalone domain-rules file, or constraints added on top of extracted spec content. Omit for files that are purely descriptive or reference content (e.g. an extracted REPORTS or INPUTS section) with nothing to enforce beyond what's already stated there. Each rule is a MUST by default - no "Must:" label needed. Use a flat or numbered list; number items if they need to be referenced elsewhere (e.g. from the checklist). Negative constraints ("do not...") belong in EXPLICIT NON-GOALS below, not here.}


ALGORITHM / REQUIRED CHECK {OPTIONAL}
{Use when correct behavior requires calculation, ordering, comparison, reconciliation, state transition, or exhaustive checking. A rule states WHAT must be true; an algorithm states HOW the GPT establishes that it is true — inputs, the transformation/check sequence, the completion condition, the failure condition, and what triggers recomputation. Do not assume the model will derive an algorithm from prose rules alone. Omit when every rule in this file is a simple, single-step check.}


NAMING CONVENTIONS {OPTIONAL}
{Use only when the output requires deterministically derived names (e.g. test class names from function names). Give the exact derivation rule plus one worked example. A fixed set of allowed values (e.g. a status vocabulary) is not a naming convention — put it in RULES as its own subsection.}


INVARIANTS {OPTIONAL}
{Use for conditions that must always remain true, especially around high-risk failure conditions where conflating two things would let bad output pass silently (e.g., 'entry fidelity does not imply temporal completeness'). PASS/FAIL CONDITIONS {OPTIONAL}
